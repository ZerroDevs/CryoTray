It parses `Off` / `AutopilotOnly` / `AlwaysOn`, normalizes 5000/10000 hundred-nanosecond targets, clamps to `NtQueryTimerResolution` bounds, and never holds without a successful `NtSetTimerResolution`. `ApplyCore` is driven by settings changes, `AutopilotService.StateChanged`, `SystemEvents.PowerModeChanged`, and startup; release is paired on Off, game exit, battery, session ending, and exit.

## Domain rules

- Unavailable numeric telemetry (`CpuTemp`, `PeakCpuTemp`, `MaxCoreTemp`, `CpuGhz`, `CpuBaseGhz`, `CpuMaxGhz`, `CpuLoad`, `GpuTemp`, `GpuLoad`, `RamUsedGb`, `RamTotalGb`, `RamUsagePercent`, `DriveTelemetry.Temperature`) uses `double.NaN` (and `null` for `int?` / `double?`), never synthetic values; UI renders `--` or an unavailable message.
- `snapshot.CpuTemp` is the integer display max across mapped cores when finite sensors exist (`double.NaN` when unavailable). Hero, tray badge, overlay, chart, and stress test all check `double.IsFinite(v) && v > 0`.
- `snapshot.PeakCpuTemp` is the raw sensor peak before per-core mapping (`double.NaN` when unavailable).
- Ignore CPU temperature sensors containing `Distance to TjMax` or `SoC`.
- Peak prefers the hottest CCD Tdie when present, then Tctl/Tdie, then the hottest CPU reading, then motherboard CPU reading.
- Direct per-core sensor mapping is used only when no AMD `Tctl/Tdie` sensor exists.
- Floor is `peak - 3.5` so the bubble keeps a compact few-degree span.
- Per-core sensor names are matched by `^(?:CPU\s*)?(P-Core|E-Core|Core)\s*#\s*(\d+)$`.
- Hottest cores are every core whose `DisplayTemp` equals the maximum.
- Popup columns are 4 up to 16 cores, 6 above 16.
- Primary GPU Auto mode prefers discrete GPUs (NVIDIA, non-APU AMD, Intel Arc) with valid temperature over integrated graphics; users can override via `AppSettings.PreferredGpuIdentifier` in `Settings > GPU`.
- Storage telemetry pairs with WMI drives by normalized serial number, then `PhysicalDriveNumber`, then model name + closest capacity, never by positional index.
- Excluded storage drives (`AppSettings.ExcludedDrives` keyed via `HardwareMonitorService.GetDriveExclusionKey`) are omitted from `MainWindow` SSD rows, `TemperatureAlertService` disk notifications, and `StorageHealthAlertService` health alerts.
- `SystemInfoQueryService` CPU temp stats (`System_TempStats`) report `CoolingModeActive == true` samples only (`TelemetryRingBuffer.GetCpuStats(coolingOnly: true)`).
- Hotkey recorder accepts standalone `F1-F12` or modifier (`Ctrl`/`Alt`/`Shift`/`Win`) + `A-Z`, `0-9`, or `F1-F12`.
- Motherboard fan sensors are collected from non-CPU, non-GPU, non-storage hardware and their subhardware, deduplicated by hardware identifier plus sensor name; raw non-negative readings including 0 RPM are retained in `HardwareSnapshot.Fans`, while `FormatFanSpeeds` hides stopped headers and renders `--` when no fan is moving.
- Fan Health Watch arms a header only after 60 s continuously at or above 300 RPM. It alerts only after 30 s at 0 RPM, and only when CPU or GPU load is at least 25% together with a temperature of at least 60 °C sustained for 15 s. ## Stress Test Retained Throughput

- **Per-Phase Iteration Accounting (`Views/StressTestWindow.xaml.cs`, `Models/TelemetrySample.cs`)**: Each `BelowNormal` stress worker owns a `long` iteration counter and publishes it with `Volatile.Write` every 1024 loops. `TakeIterationRate` sums the counters at each 1 Hz telemetry tick, divides by elapsed stopwatch seconds, and stores the result in `TelemetrySample.StressIterationsPerSecond`. The tick that first observes a Cooling ON/OFF change is stored as `NaN` so the mixed interval is excluded. `ComputeCoolingComparison` averages valid rates over the same trailing 5 samples as temperature and power, then renders `OnRate / OffRate * 100` through `Stress_PerformanceRetained` (`Performance retained: 93%`) under the delta. The workload uses a changing `Math.Sqrt` + `Math.Sin` accumulator so the JIT cannot fold it to a constant. `ComputeFpsImpact` clamps the percentage to `0..100`, scales the user-selected FPS reference (`60/100/120/144/165/240`, default `100`, persisted as `AppSettings.StressFpsReference`), and renders `Stress_FpsImpact` (`If 100 FPS: ~84 FPS (16 lost)`) under the retained line; `CmbFpsReference` saves a preset through `SettingsService` and refreshes the line immediately; `Stress_FpsImpactHint` states that this is only an estimate for CPU-bound games and that actual loss may be less or more depending on the game, GPU, threads, and frame pacing.

## GPU Power Control Architecture

- **Opt-in boundary**: `GpuPowerControlEnabled` defaults false. No backend is constructed for write purposes until the user enables the feature; normal telemetry remains read-only through LibreHardwareMonitor. Enabling queries native bounds and applies the VBIOS default (100%) rather than a preset. `GpuReapplyPowerLimitOnStartup` defaults false; when unchecked a persisted enabled state starts at the native default.
- **Backend mapping**: `NvapiPowerBackend` loads `nvapi64.dll` exclusively from `%SystemRoot%\System32` through `NativeLibrary.Load(..., DllImportSearchPath.System32)` and resolves power-policy info/status/set through `nvapi_QueryInterface` IDs `0x34206D86`, `0x70916171`, and `0xAD95F5ED`. `AdlxPowerBackend` loads `amdadlx64.dll` from System32 and calls the documented ADLX C ABI directly through its COM-like vtables (`GetGPUTuningServices` → `GetManualPowerTuning` → `GetPowerLimitRange` / `GetPowerLimit` / `SetPowerLimit`), so no native C++ shim is needed. ADLX reports power limits as signed offsets from the VBIOS default (for example `-30..+10`), so the backend converts to absolute percentages (`100 + offset`) for the UI and converts back before writing. `AdlPowerBackend` remains the fallback for older driver packages and uses ADL2 OverdriveN capabilities plus `PowerLimit_Get/Set`. Intel and locked/laptop VBIOS ranges fail closed with the exact unsupported badge.
- **Safety**: all calls serialize on `SemaphoreSlim(1, 1)` on a background task, preset/slider values clamp to fresh VBIOS bounds and never above 100%, every write is read back, and the factory default is restored on toggle-off, normal exit, `DispatcherUnhandledException`, `AppDomain.UnhandledException`, and `SystemEvents.SessionEnding`. Toggle-off restores when the feature is still enabled even if another tool changed the cap. `RestoreForExit` waits up to 3 seconds so shutdown cannot hang on a driver; `Dispose` calls it before marking itself disposed.
- **No duplicate telemetry**: board watts, core temperature, and hotspot continue to come from the existing `HardwareMonitorService` snapshot. `GpuPowerControlService` only reads the cap through the vendor backend.
- **Documentation boundary**: `SECURITY.md` treats System32-only vendor loading and the timer's fixed power action as separate trust boundaries; `README.md` and `CONTRIBUTING.md` state the same opt-in, clamp, restore, warning, and cancel contract.

## Download-Completion Timer Architecture

- `DownloadTimerEnabled` defaults false. `DownloadTimerEngine` is a pure one-second state machine used by `DownloadTimerService`; it waits for an active download when configured, accumulates a quiet window below the selected threshold, blocks on disk writes at or above 2 MB/s, fails closed if PDH disk sampling is unavailable, and runs a 60-second topmost warning before executing the selected power action.
- The engine cancels a pending warning if download or disk activity returns. A manual cancel or a fired action auto-disarms and persists false, preventing a wake-from-sleep loop. Network sampling sums received-byte deltas across Up, non-loopback, non-Tunnel adapters; disk writes use `\PhysicalDisk(_Total)\Disk Write Bytes/sec` through PDH.
- `App` owns the topmost `DownloadTimerWarningWindow`, handles status countdown updates on the dispatcher, starts/stops the service from `SettingsService.SettingsChanged`, exposes the same toggle in the tray menu, and stops the timer on session ending.

## Adaptive Update Checks & Update UI

- `App.ScheduleAutomaticUpdateCheck` uses a 5-minute timer while the dashboard is visible and a 30-minute timer in the tray. Startup runs an immediate check, and `PowerModes.Resume` plus `NetworkChange.NetworkAvailabilityChanged` trigger a throttled immediate check. `AutomaticUpdateChecks` remains the gate; `UpdateStatusService` records the last checked time, outcome, version, and detail and persists them in `AppSettings` so About survives restarts.
- `App.AvailableUpdate` holds the newer `ReleaseInfo` (or null) and `UpdateAvailabilityChanged` tells an open dashboard to refresh. The once-per-version tray balloon still uses `LastNotifiedUpdateVersion` and is suppressed by `DisableAllNotifications`; its click opens About with the release.
- `MainWindow.UpdateBanner` is a 44 px translucent strip with **Update**, **About**, **Later**, and **Skip**. Later stores `UpdateSnoozedVersion`/`UpdateSnoozedUntilUtc` for 24 hours; Skip stores `DismissedUpdateVersion`. A snooze timer restores the strip when the window expires. `UpdateSuccessBanner` is a green 44 px strip shown from `App.PendingUpdateSuccess`, with a 20-second auto-hide and an X; it is consumed on hide or window close.
- `ReleaseInfo.ReleaseNotes` carries the normalized GitHub release body. Settings > About shows it in a small scrollable box, plus last checked time, the last failure detail, and a Cancel button beside the update action. `UpdateStatusService.Changed` and the About tab selection refresh that state.
- The banner's Update button calls `OpenSettingsDialog(true, update, true)` and About calls `OpenSettingsDialog(true, update, false)`. `SettingsWindow.PendingUpdate`/`PendingUpdateInstall` are consumed in `Loaded`; `ShowAvailableUpdate` selects About and sets notes, while `BeginUpdateInstall` reuses `InstallUpdateAsync`.

## Update Security & Download Resilience

- `UpdateStorage` owns `%ProgramData%\CryoTray` as Administrators with a protected Administrators/SYSTEM DACL. It rejects reparse points on the root and all children, recursively secures existing children, and clears untrusted pre-existing root contents. The log rotates at 1 MiB; downloads older than seven days are pruned. Settings are outside this root.
- Elevated application copies must live in an administrator-protected location. `UpdateStorage.IsSafeApplicationLocation` checks the application directory owner and any standard-user write/delete rights, then walks every existing parent and rejects untrusted owners plus delete, delete-child, change-permission, and take-ownership rights, ignoring inherit-only ACEs; reparse points are rejected. `App.OnStartup` exits with `Update_UnsafeLocation` when this fails, otherwise `EnsureApplicationDirectoryProtected` sets an Administrators owner and a protected Administrators/SYSTEM DACL plus Builtin Users read/execute on the app directory and every child. Installed copies use Program Files; portable copies are supported only from a protected folder. `UpdateService.LaunchUpdater` repeats the guard and protection before starting the helper.
- `UpdateService.DownloadAsync` uses one stable release/asset work directory, a non-sharing `download.lock`, a 15-minute per-attempt timeout, three attempts with jittered backoff, Range/If-Range resume through `.part`, `Retry-After` handling, a 512 MiB cap, and a free-space check. Metadata retries timeouts and 5xx/408/429 but not permanent 4xx. The API request sends `X-GitHub-Api-Version` and conditional `If-None-Match`.
- `UpdateService.LaunchUpdater` uses the absolute System32 PowerShell path with `-NoProfile -NonInteractive -File`, passes the expected SHA-256, version, backup path, update ID, and `/PRESERVEUPDATE` to the Inno helper, and checks the application location plus reparse points on target paths. The helper validates `update-manifest.json` (`version`, `files`, per-file SHA-256 `hashes`, safe `delete` paths), copies, deletes stale files, runs the installer silently, and writes `AppliedUtc` only after success. A failure restores the verified backup and clears the pending marker.
- `UpdateInstallationService.IsInstalledAt` classifies a copy as installed only when an Inno uninstall key matches its directory, or when it is under Program Files and contains Inno's `unins000.exe`. A portable copy under Program Files without that marker stays portable. Installed copies require the setup executable; portable copies prefer `CryoTray-Update-*.zip`, which carries the hashed manifest. The release workflow signs the app before Inno compiles the setup, signs the setup afterward, and builds a cumulative delete list from the previous manifest's `files` and `delete` history. If a previous release exists but no baseline archive is readable, packaging fails instead of publishing an empty delete list.
- `UpdateCompletionService` records the from/to versions plus a one-time update ID before launch. The new app shows the success strip only after the helper writes `AppliedUtc`, and consumes the marker when the strip closes. `Installer/CryoTray.iss` clears a stale marker during manual installation unless the helper passes `/PRESERVEUPDATE`; installed copies force the default Program Files path with `DisableDirPage=yes`, `UsePreviousAppDir=no`, and run `icacls /setowner` so the app folder and files are owned by Administrators. `UpdateStatusService` restores the persisted last-check time, outcome, version, and detail from `AppSettings` at startup; a persisted `Available` shows **Check again** until a fresh check supplies the release object. Authenticode remains best-effort; unsigned payloads are allowed.
- **Rollback-root hardening (2026-11-19):** `App.OnStartup` now calls `UpdateStorage.EnsureUpdateRoot()` and `EnsureRollbackRoot()` before `UpdateCompletionService.ReadPending()`. `UpdateBackupService.GetCurrent()` secures the rollback root before opening `backup.json`, `UpdateService.LaunchRollback()` secures it before validating the requested directory, and `ReadPending()` secures the update root. `SecureDirectory()` rechecks reparse points after `Directory.CreateDirectory()`. The test suite creates a pre-existing inherited-ACL rollback root with an attacker-authored manifest and verifies `GetCurrent()` clears it and returns no backup. The installer also removes a previously registered Inno custom installation after a successful Program Files install when the old path is a real CryoTray install and is not a protected, overlapping, or system path.

## Settings Notifications & Fan Names Disclosure

- `AppSettings.DisableAllNotifications` defaults to `false`. `App.ShowTrayNotification` returns before `TrayIconManager.ShowNotification`, so every tray balloon that goes through the app is suppressed, including temperature, fan health, storage health, update, memory optimization, and both test buttons. `RunAutomaticUpdateCheckAsync` skips `LastNotifiedUpdateVersion` while the switch is on, so re-enabling can still surface an available update. `MemoryOptimizerService` also skips its completion notification.
